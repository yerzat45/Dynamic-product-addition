# Profitbase → Битрикс24: товары сделки

Node.js 20+ • без сторонних npm-пакетов • готово для Git.

## Что делает

Когда Profitbase заполняет поля объекта в сделке, БП вызывает сервис с `dealId`. Сервис самостоятельно считывает сделку через REST, берёт **ЖК** (`UF_CRM_1789104591`), **название дома** (`UF_CRM_1789104577`) и **номер помещения** (`UF_CRM_1789104515`), собирает имя вида:

`Квартира №3 — Swiss Residence, Блок 11`

Ищет **точное** название в товарном каталоге Битрикс24 через `crm.product.list`. Если совпадение единственное, проверяет товары сделки. В режиме `append` добавляет товар при отсутствии, сохраняя другие строки. Повторные вызовы не добавляют повторно тот же товар. В режиме `strict` заменяет все товарные строки одной правильной строкой (внимание: удаляет другие товары!).

**Важно:** `append` предотвращает ошибку добавления через этот сервис, но не блокирует ручное изменение товара менеджером. Если требуется принудительная защита, после согласования включить `strict` + настроить автозапуск после изменения сделки и права на изменение товаров; `strict` удаляет все прочие товарные строки. Сервис сам не подписывается на события Profitbase и не устанавливает запреты в интерфейсе.

## Установка на Ubuntu

```bash
sudo mkdir -p /opt/projects/profitbase-bitrix-sync
# скопировать сюда содержимое репозитория
cd /opt/projects/profitbase-bitrix-sync
cp .env.example .env
nano .env
node --version  # требуется v20+
node --test
node src/server.js
```

В `.env` указать HTTPS webhook адрес REST от технического пользователя Битрикс24 с разрешениями CRM и `SYNC_TOKEN` (случайная длинная строка). На первом запуске **DRY_RUN=true**, `SYNC_MODE=append`. Не публикуйте `.env` и webhook URL в Git.

## Как вызвать из БП

**Лучше POST:** отправить HTTP-запрос на `https://ВАШ-ДОМЕН/sync`, тело `dealId={{ID_СДЕЛКИ}}`, заголовок `X-Sync-Token: ЗНАЧЕНИЕ_SYNC_TOKEN`.

**Если действие БП поддерживает только ссылку:**

`https://ВАШ-ДОМЕН/sync?dealId=123&token=ВАШ_SYNC_TOKEN`

Подставьте ID текущей сделки через редактор вставки значений БП (не фиксированное `123`). **GET с токеном в URL менее безопасен**: токен может попасть в историю, proxy access log и журнал БП; для продакшна выбирайте POST + заголовок. В БП разместить запуск **после записи Profitbase всех трёх полей**, а не до; при асинхронном обновлении настройте отложенный повторный запуск. Удалить/выключить старые активности `CrmAddProductRow`, иначе они продолжат добавлять товары независимо от сервиса.

**Примечание:** конкретный блок HTTP-запроса зависит от редакции и тарифных возможностей Битрикс24. Если в вашем БП отсутствует действие исходящего HTTP-запроса, можно использовать исходящий вебхук/робот или промежуточный обработчик; не требуется импортировать новый BPT.

Тест:

```bash
curl -sS -X POST https://ВАШ-ДОМЕН/sync \
  -H "X-Sync-Token: ВАШ_SYNC_TOKEN" \
  -H 'Content-Type: application/json' \
  --data '{"dealId":123}'
```

При `DRY_RUN=true` ответ покажет `action` (`append`, `replace` или `noop`), но НЕ изменит сделку. После проверки реальных результатов и резервирования тестовой сделки переключить `DRY_RUN=false`, перезапустить процесс.

## Размещение за Nginx

Локальный слушатель по умолчанию `127.0.0.1:3080`, внешний TLS — через Nginx. Пример `examples/nginx.conf` замените своим доменом; SSL-сертификат настраивается отдельно.

## systemd

Скопировать `examples/profitbase-bitrix-sync.service` в `/etc/systemd/system/`, поправить пользователя и путь, затем:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now profitbase-bitrix-sync
sudo journalctl -u profitbase-bitrix-sync -f
```

## Ограничения и безопасность

- Нет совпадения, есть дубли, пустые поля или неожиданный формат — **никакого изменения**.
- Цена товара берётся из `crm.product.list` в текущем каталоге. Нулевую цену сервис считает допустимой (в предоставленных экспортных файлах такие позиции есть). Для требований к цене и валюте необходим отдельный бизнес-регламент.
- Поиск через `=NAME` зависит от сервера Битрикс24. Дальше выполняется строгая нормализованная проверка имени. Параметры фильтра необходимо проверить на тестовой сделке.
- Многократные события после изменения сделки могут вызывать сервис повторно: `noop` безопасен. Локальный lock работает только в одном процессе, для нескольких инстансов требуется распределённая блокировка.
- Переустановка `strict` не транзакционная; конкурирующие изменения между проверкой и записью теоретически возможны. Ограничьте правки товаров на время синхронизации.
- API возвращает техническое сообщение ошибки только после успешной авторизации; секрет REST наружу не выдаётся.
- Часть объектов Profitbase может не иметь товарного аналога. Перед продуктивным запуском проверить каталог и соответствие выгрузок (см. `docs/source-analysis.md`).
